# 03 执行：一张工单，一个 Session，一个目录

> **结论先行**：工单被接受后，执行器在**自己的 DSH Session**里、围绕**自己的目录**完成工作：先跑 prepare 命令准备 checkout/worktree，再调查、实现、验证、提交、开 PR。执行器不向人提问（问题通过报告结构化上交），前台命令 5 秒转后台，失败可重试，重启带恢复说明，整个系统可以暂停处理。

**如果只记三件事**：

1. **隔离到工单**：Session 名是 `worker-<ticket id>`，目录按工单短名创建，互不覆盖；分支通常是 `agent/<短名>`。
2. **长任务不堵人**：前台 shell 5 秒转后台；回合结束时后台最多再跑 30 分钟；子代理可继续，交接给人时子代理停止、shell 作业可留作演示。
3. **失败可恢复**：瞬时模型/网络错误自动重试三次；`blocked`/`failed` 工单暂停自动输入，等人或 retry；进程重启后按恢复说明继续。

## 0. 口径

| 概念 | 说明 |
|-|-|
| Executor | 执行器：为一张工单运行一个 DSH Session 和目录的组件 |
| Executor Session | 执行器 Session，`worker-<ticket id>`；与主 Session（orchestrator）分开 |
| Assignment | 一次"把工单交给执行器"的绑定；retry/restart 会产生新的 Assignment |
| Report | 执行器向工单报告的状态：progress / waiting / ready / blocked / failed / dropped |
| Attention | 工单上等待人回答的结构化问题 |

## 1. 目录与准备

- 执行根目录由部署配置，每张工单一个子目录，目录名是工单短名。
- 第一次 Assignment 前，如果目录不存在，就跑一次 **prepare 命令**（`sh`，10 分钟超时，在工作根目录执行）。典型命令是 `git worktree add`，从本地克隆创建工单分支。
- 没有 prepare 命令时，worker 从空目录开始；prepare 失败会让工单失败并保留输出，修好后可以重试或由人的消息触发再准备。
- **PR 归属**：分支最后一段等于工单短名时，PR 自动归属该工单；执行器也可以在报告里声明 PR。

## 2. 运行环境

执行器和 prepare 命令共享同一组**执行变量**（不含凭据）：

| 变量 | 含义 |
|-|-|
| `DSH_SUPERAGENT_DIR` / `NAME` / `TICKET` | 工单目录、短名、id |
| `DSH_SUPERAGENT_BLOCKED_COMMANDS` | 禁止调用的命令名，空格分隔 |
| `DSH_SUPERAGENT_GITHUB_REPOSITORY` / `ACCOUNT` / `COMMIT_EMAIL` | 监听的仓库、代理账号、提交邮箱 |
| `DSH_SUPERAGENT_GITHUB_NUMBER` / `PR_HEAD` | 触发工单的 Issue/PR 编号，以及 PR 的 head ref |
| `DSH_SUPERAGENT_FEISHU_BOT` / `CHAT` | 飞书机器人、发起工单的群 |

- **命令包装**：`<stateDir>/worker-bin` 在 PATH 最前，`gh` 指向代理账号的 CLI，`lark-cli` 指向 bot 身份的配置，被禁止的命令直接失败。
- **git 配置**：`<stateDir>/worker-gitconfig` 替换操作者的全局/系统 git 配置，用代理账号做 github.com 凭据、把 SSH 地址改写成 HTTPS、定义 LFS 过滤器；不设置提交身份，也不允许交互式凭据。
- **工具面**：worker 有 bash、文件读写、搜索、后台作业、子代理、`orchestrator_read`/`report`/`ack`/`handback` 等；没有 `ask_user_question`、`present`、`plugin_manager`，因为执行器无人值守。
- **边界**：这些包装建立默认值，**不是安全沙箱**；worker 以操作者 OS 用户、`danger-full-access` 运行，可以按绝对路径执行程序、读家目录。需要真隔离时用专用系统账号。

## 3. 并发、后台与交接

- **槽位**：`maxWorkers` 控制同时运行的执行器（本实例 3）。人的消息或状态请求可以多用 1 个槽，确保人不会被新工单饿死；CI 等自动输入排队等普通槽。
- **前台转后台**：worker/router preset 在前台命令 5 秒后把它移到后台作业，让执行器能在下一步收到新消息；DSH 标准子代理在 60 秒后转后台。
- **回合结束后的后台**：最多再跑 30 分钟；到点 shell 作业被杀、工单报 `waiting`，并说明杀了哪些作业、哪些子代理仍在跑。子代理允许继续，结果在下一回合读取。
- **交接给人**（`ready` 或结构化提问）：立刻释放槽位；子代理停止；shell 作业（例如留给人看的本地服务器）可以继续到 Assignment 结束，且完成时不唤醒执行器。
- **Assignment 结束**：杀掉 shell 作业，释放子代理，丢弃它们唤醒的回合；替换的 Assignment 在其后启动。
- **子代理**：worker 的子代理用 DSH `standard` preset，继承 worker 的工具与权限；嵌套深度和并发数由部署配置限制（本实例深度 ≤3、每棵树活跃子代理 ≤30），工单结束时收回工具。

## 4. 失败、重试与恢复

| 场景 | 行为 |
|-|-|
| 模型/网络瞬时失败（408/429/5xx、连接拒绝/重置/超时） | 自动重试三次，退避增长；启动失败重新启动，回合失败让 worker 继续；prepare 失败不重试 |
| `blocked` / `failed` 报告 | 工单暂停自动输入；CI/bot 消息只记录不投递；人的消息、后续非 blocked/failed 报告或 retry 解除 |
| 输入投递失败 | 工单显示"输入未送达"，按 2 秒起、翻倍至 1 分钟重试 |
| 人点 **Retry** | 结束当前 Assignment，在同一 Session、目录、分支和 PR 上重开，接管等待中的输入 |
| 进程重启 | 运行中的 Assignment 以"host restarted"结束；新 Assignment 带恢复说明，要求先检查目录、git 历史和 GitHub 再重复外部动作；重启顺序按最老工单优先 |
| 暂停处理 | 停止派发、新评估、评估超时、输入投递和回复；来源继续记录，运行中的回合不打断；已启动的 launch 等恢复后再继续 |
| 无效来源配置 | 该来源实例被禁用，其余照常 |

- 所有"决定之后要做的事"（转达、投递、启动、回复）先落库再执行；每类工作有自己的持久队列、退避和健康项，连续失败三次才在概览显示为系统问题（输入投递失败显示在工单上）。
- 重试/重启会把被替换 Assignment 中**未读**的消息重新投递；已经进入 Session 历史的不会重复。

## 5. 一次典型执行

| 时间 | 发生什么 |
|-|-|
| T+0 | 飞书/ GitHub 收到 @，来源过滤并生成 Trigger；主 Session 研判后 accept |
| T+1s | 创建工单、Mandate、订阅和确认；用户收到一句"在做 X" |
| T+2s | 启动 Assignment：prepare 建 worktree；`worker-<id>` Session 起来 |
| T+3s– | worker 读需求、看代码、实现、跑检查；前台命令 5 秒转后台 |
| 中途 | 线程里的新消息、CI 结果、review 评论作为 Input 到达；worker 判断归属 |
| 完成 | 提交、push、开 PR；报告 `ready` 并绑定 PR → 面板显示"待审阅" |
| 之后 | 评审意见/CI 继续唤醒工单；PR 合并或关闭后工单结束并发一次通知 |

## 6. 这套设计的取舍

- **好处**：工单之间互不踩目录、可以并行；长任务不阻塞主 Session；失败可重试、重启可恢复；人始终能直接进入 Session 接管。
- **代价**：每个工单要付一次 prepare 和 Session 启动成本；同仓库多工单并发时，worktree 和依赖缓存需要运维规划；30 分钟后台上限意味着超长任务要么转子代理，要么分段续跑。
