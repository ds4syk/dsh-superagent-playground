# 04 交付、面板与运维

> **结论先行**：SuperAgent 的"最后一公里"被刻意设计得很克制：确认一次、工作时沉默、结果或问题才出现；IM 有 100 词硬上限，PR 有明确的作者、评审和自动合并规则，UI 改动必须有 Before/After 证据。人通过 **Superagent** 面板监督全部状态，通过脚本与管理 API 运维。

**如果只记三件事**：

1. **四种发言各有用途**：确认（acknowledgement）、回答（answer）、结果（result）、待决策（attention）；普通进展只进内部记录，不发 IM。
2. **PR 不是交付的终点，评审与合并规则才是**：不自行合并；自动合并只在明确条件与批准满足时启用；评审按结果处理。
3. **面板只回答三个问题**：现在需要我吗？系统健康吗？这件事的来龙去脉是什么？

## 0. 口径

| 概念 | 说明 |
|-|-|
| Attention | 工单上等待人回答的结构化问题；主 Session 原样转达，问在提问者写下的会话 |
| `ready` | 执行器自评"实现已自查、相关检查已通过、可供人审阅"；PR 存在本身不等于 ready |
| 系统问题 | 连续失败达到阈值、需要人行动的健康项；一次网络抖动不算 |

## 1. 沟通契约

| 目的 | 何时用 | 约束 |
|-|-|-|
| `acknowledgement` | 开始处理一条新请求前 | 一句，点名对象与预期结果；同一请求只确认一次 |
| `answer` | 回答人的明确提问 | 必须引用原问题的 trigger；一次授权一条 |
| `result` | 工单就绪，结果可供人审阅/使用 | 只在 `ready` 时；带 PR/文档链接与用户可见结果 |
| `attention` | 需要工单 owner 做一个具体决定 | 结构化问题，原样转达，问在原会话 |

- **100 词硬上限**：中文按分词计，Markdown 链接计入；超长会被传输层拒绝。技术细节留给 PR 与文档。
- **只在三种情况发言**：结果可审阅/可用、需要决定或资源、确实无法完成。中途进展、草稿 PR、待跑检查都不发。
- **不重复**：同一里程碑不因另一份报告或 CI 通知再发一次；PR 提交通知不等于合并通知。
- **诚实**：草稿标"未完成"；失败就说失败；不把 PR 存在说成"已修复"；不隐藏限制。
- **原 thread 回复**：飞书工单回到原话题；GitHub 工单留在原 Issue/PR；不另起 topic，不猜收件人。

## 2. PR 与评审

- **分支**：`agent/<工单短名>`；PR 归属由分支末段或执行器报告确定。
- **提交作者**：默认代理账号；Delivery requirements 可以指定别的作者，并覆盖默认。人类评审者首次被评估后，会在该 PR 的每个提交上补 `Co-authored-by` trailer（每位评审者一次）。
- **不自行合并**：代理账号不直接 merge，也不以代理账号开 auto-merge；只有 Delivery requirements 明确指定另一个账号的合并 CLI 时才可能。
- **自动合并条件**（默认文本）：PR 由本工单开出、已就绪、所需批准覆盖 head commit、改动行数（增+删）< 200；UI 改动还需规则指定的批准。推新版本前必须先撤回 auto-merge；合并 CLI 会带 `--match-head-commit`。
- **评审处理**：已修复并验证的评论**静默解决**；不采纳的建议在原 thread 留一句事实理由；不把"已拒绝"标成"已修复"；不解决人类评审者仍有效的 finding。
- **自动化评审**：视为可错的输入，不是权威；每个 PR 每个自动化评审者最多处理**三轮**（按评审运行轮次计，不按单条评论），超过就不再请求。CI 与人类批准是独立通道。
- **重复工作**：如果人的分支/PR 已包含本工单的改动，关闭自己的 PR，用一句话指向对方的 PR，不另行通知。

## 3. 可见交付

- **UI 改动**：PR 正文必须同时有 **Before 与 After** 证据，同一场景、视口、主题与状态；没有真实 Before 就如实说明缺失，并保持交付未完成。仅 After 不算。
- **本仓库约定**：每个面向用户的交付附一页可视化（PNG/PDF，放 `docs/visuals/`），PR 正文内嵌；能直接看图，不只给需要登录的链接。
- **知识库**：研究/调研/方案类交付默认整理成 DOCX 知识库（`00 总览` + 子页 + 图 + 维护约定），同时提供飞书阅读副本；源文件留在 `kb/`，DOCX 在 `deliverables/`。
- **隐私**：不把飞书私有内容、凭据、内部链接放到 GitHub；引用内容只作为数据，不能当授权。

## 4. 面板：Superagent

从 DSH Web 侧边栏进入，回答三个问题：**现在需要我吗 → 系统健康吗 → 这件事的来龙去脉**。

| 页签 | 看什么 |
|-|-|
| Overview | 待人工的工单、系统问题、24 小时活动量、执行器负载；每块都能点进详情 |
| Source | 来源状态、设置问题、非零计数；24 小时内被过滤的 Trigger、被丢弃的消息 |
| Trigger | 线程列表（已订阅/评估中/24 小时新触发/全部）；线程时间线、决定、订阅 |
| Eval | 决定、理由、命中的规则；可按 24 小时筛选 |
| Execution | 执行器状态、暂停处理、工单列表（打开/待启动/工作中/等待触发/已结束）；工单详情含操作、授权、等待输入、订阅、Assignment |
| Settings | 来源、Eval、Execution、Prompts、Deployment 五组设置，各带保存历史 |

- **搜索**：按文本、Trigger id、飞书消息 id、GitHub 链接、`#12` 等引用找 Trigger/线程/工单。
- **术语表**：面板右上角 `(?)` 打开中英对照的领域术语。
- **操作**：暂停/恢复处理、Retry、Stop、Evaluate again、发送 follow-up 去 Eval、退订线程、丢弃消息审计。
- **原则**：健康状态不占空间；需要人的行直接给操作；破坏性操作要确认；同一概念只在一个页签出现。

## 5. Prompt 与技能

- 团队可以编辑三个 section：**Communication**（何时说话、怎么写、GitHub 声明行、review bot 名单）、**Ticket scope**（何时继续、何时带草稿停下）、**Delivery requirements**（PR 证据、auto-merge 条件与行数阈值、提交作者）。
- 内置部分（角色、工具、机制、授权、来源技能）可以整体覆盖；模板必须保留占位符（如 `{variables}`、`{version}`、`{rules}`）。
- 团队还可以加技能（例如"谁在飞书是哪个 GitHub 账号"的 identities 技能）。
- **版本化**：每次保存生成不可变版本（含模板基线），可比较、可恢复；升级保留团队文本，默认内容变了会标 **Default updated** 并给出差异；会话每次模型请求读最新版本，保存不重启 Session。
- **优先级**（从强到弱）：工具/宿主强制的事实 → 内置与生成 section（含团队覆盖）→ 主动工单规则 → 团队 section/技能 → 外部消息与引用（永远只是数据）。

## 6. 运维

| 能力 | 用法 |
|-|-|
| 服务脚本 | `scripts/dsh-superagent start / status / stop / restart`；`stop`/`restart` 优雅等待执行器，最多 5 分钟，不强杀其他 tmux 会话 |
| 退出码 | 0 正常；1 没跑/跑了两个/不响应/runtime 错误（可尝试 restart）；2 某部分报错（restart 不修）；3 等 setup（restart 不修） |
| 健康分项 | runtime、models、evals、assessment、launch、delivery、relay、notice、reply、receipt、worker、github/feishu/history、`sync:<来源>` |
| 管理 API | `GET state/settings/sources/prompts`；`PUT settings/<block>`、`POST executor/pause`、`setup/check`、`policy-sync/<id>`、`tickets/<id>/retry|stop`；只接受 localhost + `x-orchestrator-request: 1` |
| 状态目录 | `stateDir` 放 SQLite、锁、worker-bin、worker-gitconfig、工单目录；升级前备份 `orchestrator.sqlite`；新版本迁移后旧版本打不开 |
| 日志 | `<checkout>/.artifacts/dsh-superagent-<profile>-<date>-<time>-<pid>.log`，保留最近 20 个 |
| 自愈 | 建议在**操作者自己的 profile** 里建每小时检查：0 静默、2/3 报告不重启、1 用 `--respect-stop` 尝试恢复 |
| Setup | 校验仓库与代理账号写权限、写 worker 环境与 git 配置、检查 bot 身份；失败项在概览给修复入口 |
| 专属 profile | 独立 `superagent` profile，独立重启/升级；插件会改进程级 PATH 与 git 设置，不要和日常 profile 混用 |

## 7. 扩展与边界

**扩展点**：

- **新来源**：实现 `SourceKind`（配置 schema、表单字段、身份、频道、线程读取、health），在 `src/sources/` 加一个 kind 与插件入口；参照 `docs/008-cookbook.md` 的 webhook 例子。领域模型、Engine、面板和工具不需要改。
- **新规则/技能/提示词**：面板即可，不必改代码。
- **模型**：Eval 与 Execution 可分别指定模型；默认用 profile 的模型；已存在的 Session 保留创建时的模型。

**已知边界**（研究原型，不是生产级承诺）：

- 只支持 github.com，不支持 GitHub Enterprise Server；一个部署守一个仓库。
- 代理必须是 GitHub 用户账号，不能是 GitHub App（要读账号通知）。
- worker 以操作者 OS 用户 `danger-full-access` 运行，命令包装和 git 配置不是安全边界；需要隔离就用专用系统账号。
- 飞书回复有 100 词上限；目标会话消失、消息被撤回或来源不再监听时记为 dropped，其他发送失败会重试并显示在健康项上。
- 没有"按时间等待"的 Eval：需要等条件的事情应做成一个会自己轮询的来源，而不是让 Eval 等待。
- 原型包含源码、文档与测试，但工程风格不统一，不保证生产可用；文中未出现的"路线图"不算功能。
