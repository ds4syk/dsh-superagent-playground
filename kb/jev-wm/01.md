# 01 JEV 是什么：决策模型与生成式 LLM 的分工

> **结论先行**：JEV 不是「更小的聊天模型」，而是把输出空间预先限定为选项、直接从内部表示读出概率的**决策模型**。它擅长「从给定文本里读出该选哪个」，不擅长「把没写出来的后果推导出来」；这两类任务的边界，决定了它能不能当世界模型。

**如果只记三件事**：

1. JEV 的接口是 `state + 若干 typed questions -> 每个选项的概率`；一次请求内所有问题共享 state、并行打分，不生成文本。
2. 官方口径是输入 $0.042/MTok、输出免费、端到端 70–500ms；独立探测的中位延迟约 57.5ms（360 tokens），30k tokens 约 218ms。
3. 它不是开权重模型，不能微调；选项必须预先枚举（上限 255 个），没有推理链，英文最强，且在需要推导的任务上会明显退化。

## 1. 它解决的不是「生成」，是「判断」

普通 LLM 的输出是 token 序列。要做「A 还是 B」「风险多高」「要不要转人工」这类判断，常见做法是让模型生成一段文字，再解析出标签和置信度。问题是：

- 解析可能失败（格式错误、多个答案、拒绝回答）；
- 模型写出的「90% 置信」只是文本，不是经过校准的概率；
- 每个判断都要自回归解码，延迟和费用随输出长度增长。

JEV 把这条链路换成：**预先给选项，一次前向，直接读出选项上的分布**。官方把这叫 System One Model，口号是 “Decisions, not strings”。它保留了预训练 LLM 的知识，但放弃了自由生成[1][2]。

## 2. 接口与计算形态

请求体（简化）[6]：

```json
{
  "model": "jev-1.13.0",
  "state": "……一段状态描述……",
  "questions": {
    "dept":    {"type": "choice", "instructions": "哪个团队处理？", "criteria": {...}},
    "urgent":  {"type": "noul",   "instructions": "是否需要人工立即介入？"},
    "severity":{"type": "score",  "instructions": "严重程度", "criteria": ["低","中","高"]}
  }
}
```

响应给每个问题的选项概率（choice）、Yes 概率（noul）或期望分（score），并附 usage。

独立逆向分析（约 1 万次 API 探测）支持的形态是[3]：

- state 只编码一次，各 question 在自己的分支里、对同一份 state 做注意力；
- 问题之间互相读不到（把秘密放进兄弟问题，读到的概率为 0.00；放进 state 则升到 0.90–0.92）；
- 末端直接 softmax 读出，不生成解释；
- 主干「很可能是 causal Transformer + 稀疏 MoE」，但作者明确说 MoE 是最不确定的推断，换成稠密模型不影响其余结论。

> 对本报告重要的不是具体层数，而是：**它天然适合「一个 state、多个离散判断」的批量查询**，而且每次判断的成本与选项数关系不大。

## 3. 成本与延迟

官方口径[1]：

| 项 | JEV | 生成式 LLM |
|-|-|-|
| 输入 | $0.042/MTok | $0.20–$10/MTok |
| 输出 | 免费 | 约为输入的 5× |
| 端到端 | 70–500ms | 3–329s（官方对比口径） |
| 速度/成本 | 官方称 40×–200×（首页写 193.6× / 444.6×，注明是偏高的一端） | — |

独立测量[3]：360 tokens 中位 57.5ms，30k tokens 218ms，1,500 个问题 610ms；这是共享服务上的端到端时间，不是硬件基准。独立评测[12]用 346,009 次请求跑 37 个数据集，总花费不到 10 美元，与单价量级一致。

**要注意**：官方承认无法证明价格没有补贴；`jev-latest` 会漂移，复现要固定 `jev-1.13.0`。对成本敏感的场景，应按「问题数 × 输入 token」自己算，而不是只看单次价格。

## 4. 能力边界

官方 jaggedness 文档列出的弱点包括：字面理解、数学/计数、日期比较、多跳间接、长 state 中的无关细节、对抗内容、矛盾指令、选项顺序[7]。JEV-as-a-Judge 的对照实验给出了一条更清晰的边界[15]：

- 当 verdict **可以直接从文本读出**（分类、抽取、路由、打分）时，JEV 与 GPT-6 差距在 3 个百分点内，费用是后者的 **0.36%**，中位延迟 0.15s；
- 当答案**需要推导**（数学、代码、逻辑）时，JEV 落后；
- 它的置信度恰好能标出这条边界：高置信采纳、低置信升级给推理模型，能在 41% 的费用下比 GPT-6 高 0.9 个百分点。

这条边界直接对应本报告的题目：**「动作之后世界变成什么样」通常需要推导，而不是从文本里读出来**。KIIS 的 TextWorld 结果说明，在状态变量可枚举、规则简单的文本世界里，JEV 的推导能力足够好；但这不是无条件的。

## 5. 开源代理：Tacit / AnyJev / Kev

JEV 没有权重，研究只能用代理：

- **AnyJev**（Nokia，arXiv 2610.00831）：把任意开放 LLM 的一次 prefill 限制到选项 token 上读出概率；用 label prior 与选项旋转去偏，无需训练。代价是每个决策要 K 次 prefill（可用停止规则降到约 7–10 次）[10]。
- **Tacit**（AnyJev 自蒸馏，1.7B/2B/4B/8B/9B）：一次前向给出 typed decision，本报告用它作为「开权重 JEV 风格模型」。
- **Kev**（Apache-2.0，0.8B/4B/9B/27B）：基于 Qwen3.5/3.8 的 Jev 式模型族，API 兼容 TypeSafe SDK，自带 temperature；社区 Decision Index 上 Kev-27B 52.3 vs JEV 54.0，但作者说明训练数据未知，不是受控比较[19]。

代理能复现「预枚举 + 单次读出 + 概率」的契约，但不能代表托管 JEV 的全部能力。本报告的实验结论会明确区分两者。

## 6. 一句话总结

JEV 是**把「判断」做成 API** 的模型：便宜、快、带校准概率、格式不会坏；代价是只能在你预先写好的选项里选，而且不擅长把没写出来的后果推出来。把它当世界模型，本质上是在问：**我能不能把「世界变成什么样」拆成足够多的、可以从文本读出的选择题？**
