# 白话版：SuperAgent 和 AO 到底怎么接

## 一句话

**SuperAgent 是项目经理，AO 是施工队，桥接层是工单系统。**

你只跟项目经理说话；项目经理决定“在哪个仓库、做什么、该不该做”，然后把工单交给施工队；施工队负责真的改代码、跑测试、开 PR，再把“干完了/卡住了/失败了”回报给项目经理；项目经理只在你需要做决定时找你。

## 一个具体例子

你说：**“修一下 checkout 的登录 bug。”**

1. **SuperAgent（项目经理）**：判断这是 checkout 仓库的事，开一张工单（Ticket），记下“谁提的、范围、授权”。
2. **桥接层（工单系统）**：把工单翻译成 AO 能懂的话：“在 checkout 这个项目里，开一个会话，任务是修登录 bug。”
3. **AO（施工队）**：建一个隔离的工作目录（worktree），选一个写代码的 agent（Claude/Codex/DSH），让它干活；干完开 PR，跑 CI。
4. **AO 回报**：把“正在干 / 卡住了 / 干完了 / 失败了”、PR 链接、CI 结果交给桥接层。
5. **桥接层翻译**：把 AO 的状态翻译成 SuperAgent 的 Report。
6. **SuperAgent 找你**：只在需要你时说话，例如“checkout 的 PR 好了，点这里看”，或者“需要你批准一个操作”。

整个过程你**只跟一个对话 agent 说话**，不需要知道 AO 的 worktree、分支、CI 页面。这就是“人类入口与工作区解耦”。

## 为什么需要“桥”

SuperAgent 不懂 AO 的 session/worktree；AO 不懂 SuperAgent 的 Ticket/授权。桥接层只做三件事：

1. **找对工作区**：你说的“checkout”对应 AO 的哪个 project。
2. **对工单号**：同一张工单重试时，不要重复开工作目录、重复起 agent。
3. **翻译状态**：AO 的“PR 已开、CI 绿了”翻译成 SuperAgent 的“ready”；“等审批”翻译成“blocked”。

## 两套方案的实际差别

差别只有一句话：**“工单号 → AO 会话”的对应关系，记在谁那里。**

### GLM-5.4 的方案：桥自己记

- AO 只给 session 加“标签”（labels），例如 `sa.ticket=123`。
- 桥接层自己维护一张表：工单 123 → AO session 456。
- 优点：AO 改动最小，只加标签和筛选。
- 缺点：标签不是数据库唯一键。桥接层重启、或者两个请求同时进来时，可能同一个工单开了两个 session；桥要自己加锁、自己清理。

### Kimi K3.1 Pro 的方案：AO 自己记

- 创建 session 时就把 `externalRef`（例如 `sa/ticket-123/attempt-1`）写进 AO 的数据库，并加唯一约束。
- 桥接层不用自己记；重试时直接问 AO：“这个 externalRef 的 session 是哪个？”AO 只会返回同一个。
- 优点：不会重复开工；桥接层更薄，重启后也能找回。
- 缺点：AO 要改创建 session 的路径（加一个字段和唯一约束），改动稍多。

### 我建议的综合版

- **用 Kimi 的“AO 唯一键”**：解决重复开工，这是最容易出事的地方。
- **用 GLM 的“怎么找对工作区、怎么少打扰人”**：别名解析、线程粘性、60 秒合并消息、每个工作区限流。
- 结果：AO 只做合格的施工队；桥接层负责找对工作区、对工单号、翻译状态；SuperAgent 负责授权和注意力。
